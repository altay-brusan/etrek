\doxysubsection{Detailed Description}
QOpen\+GLWidget subclass to house a \doxylink{classvtk_generic_open_g_l_render_window}{vtk\+Generic\+Open\+GLRender\+Window} in a Qt application. 

\doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} extends QOpen\+GLWidget to make it work with a \doxylink{classvtk_generic_open_g_l_render_window}{vtk\+Generic\+Open\+GLRender\+Window}.

Please note that \doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} only works with \doxylink{classvtk_generic_open_g_l_render_window}{vtk\+Generic\+Open\+GLRender\+Window}. This is necessary since QOpen\+GLWidget wants to take over the window management as well as the Open\+GL context creation. Getting that to work reliably with vtk\+XRender\+Window or vtk\+Win32\+Render\+Window (and other platform specific \doxylink{classvtk_render_window}{vtk\+Render\+Window} subclasses) was tricky and fraught with issues.

Since \doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} uses QOpen\+GLWidget to create the Open\+GL context, it uses QSurface\+Format (set using {\ttfamily QOpen\+GLWidget::\+set\+Format} or {\ttfamily QSurface\+Format::\+set\+Default\+Format}) to create appropriate window and context. You can use {\ttfamily QVTKOpen\+GLNative\+Widget::\+copy\+To\+Format} to obtain a QSurface\+Format appropriate for a \doxylink{classvtk_render_window}{vtk\+Render\+Window}.

A typical usage for \doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} is as follows:\+ 
\begin{DoxyCode}{0}

\end{DoxyCode}
\hypertarget{class_q_v_t_k_open_g_l_native_widget_OpenGLContext}{}\doxysubsection{\texorpdfstring{Open\+GL Context}{Open\+GL Context}}\label{class_q_v_t_k_open_g_l_native_widget_OpenGLContext}
In QOpen\+GLWidget (superclass for \doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget}), all rendering happens in a framebuffer object. Thus, care must be taken in the rendering code to never directly re-\/bind the default framebuffer i.\+e. ID 0.

\doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} creates an internal QOpen\+GLFramebuffer\+Object, independent of the one created by superclass, for \doxylink{classvtk_render_window}{vtk\+Render\+Window} to do the rendering in. This explicit double-\/buffering is useful in avoiding temporary back-\/buffer only renders done in VTK (e.\+g. when making selections) from destroying the results composed on screen.\hypertarget{class_q_v_t_k_open_g_l_native_widget_RenderAndPaint}{}\doxysubsection{\texorpdfstring{Handling Render and Paint.}{Handling Render and Paint.}}\label{class_q_v_t_k_open_g_l_native_widget_RenderAndPaint}
QWidget subclasses (including {\ttfamily QOpen\+GLWidget} and {\ttfamily \doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget}}) display their contents on the screen in {\ttfamily QWidget::\+paint} in response to a paint event. {\ttfamily QOpen\+GLWidget} subclasses are expected to do Open\+GL rendering in {\ttfamily QOpen\+GLWidget::\+paint\+GL}. QWidget can receive paint events for various reasons including widget getting focus/\+losing focus, some other widget on the UI e.\+g. QProgress\+Bar in status bar updating, etc.

In VTK applications, any time the \doxylink{classvtk_render_window}{vtk\+Render\+Window} needs to be updated to render a new result, one call {\ttfamily \doxylink{classvtk_render_window_a81f11ddbf97ed9989f6ac2b8c8a942d9}{vtk\+Render\+Window::\+\+Render}} on it. \doxylink{classvtk_render_window_interactor}{vtk\+Render\+Window\+Interactor} set on the render window ensures that as interactions happen that affect the rendered result, it calls {\ttfamily Render} on the render window.

Since paint in Qt can be called more often then needed, we avoid potentially expensive {\ttfamily \doxylink{classvtk_render_window_a81f11ddbf97ed9989f6ac2b8c8a942d9}{vtk\+Render\+Window::\+\+Render}} calls each time that happens. Instead, \doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} relies on the VTK application calling {\ttfamily \doxylink{classvtk_render_window_a81f11ddbf97ed9989f6ac2b8c8a942d9}{vtk\+Render\+Window::\+\+Render}} on the render window when it needs to update the rendering. {\ttfamily paint\+GL} simply passes on the result rendered by the most render \doxylink{classvtk_render_window_a81f11ddbf97ed9989f6ac2b8c8a942d9}{vtk\+Render\+Window::\+\+Render} to Qt windowing system for composing on-\/screen.

There may still be occasions when we may have to render in {\ttfamily paint} for example if the window was resized or Qt had to recreate the Open\+GL context. In those cases, {\ttfamily QVTKOpen\+GLNative\+Widget::\+paint\+GL} can request a render by calling {\ttfamily QVTKOpen\+GLNative\+Widget::\+render\+VTK}.\hypertarget{class_q_v_t_k_open_g_l_native_widget_Caveats}{}\doxysubsection{\texorpdfstring{Caveats}{Caveats}}\label{class_q_v_t_k_open_g_l_native_widget_Caveats}
\doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} does not support stereo, please use \doxylink{class_q_v_t_k_open_g_l_stereo_widget}{QVTKOpen\+GLStereo\+Widget} if you need support for stereo rendering

\doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget} is targeted for Qt version 5.\+5 and above.

Returns a QSurface\+Format suitable for surfaces that intend to be used for VTK rendering.

If your applications plans on using {\ttfamily \doxylink{class_q_v_t_k_open_g_l_native_widget}{QVTKOpen\+GLNative\+Widget}}, then this format (or similar) must be set as the default format on QSurface\+Format before any widgets are created.

Note this returns a QSurface\+Format required to support the Open\+GL rendering capabilities in a \doxylink{classvtk_render_window}{vtk\+Render\+Window}. Whether those features, e.\+g. multi sampling, is actually used for rendering is determined by values specified on the \doxylink{classvtk_render_window}{vtk\+Render\+Window} instance itself through appropriate API.

Passing {\ttfamily stereo\+\_\+capable=true} is same as calling {\ttfamily QSurface\+Format::\+set\+Stereo(true)}. This is necessary if you want to use quad-\/buffer based stereo in your application.
