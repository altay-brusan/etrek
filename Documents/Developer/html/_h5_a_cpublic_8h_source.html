35/****************************************************************************
36 *
37 * structure H5AC_cache_config_t
38 *
39 * H5AC_cache_config_t is a public structure intended for use in public APIs.
40 * At least in its initial incarnation, it is basically a copy of struct
41 * H5C_auto_size_ctl_t, minus the report_fcn field, and plus the
42 * dirty_bytes_threshold field.
43 *
44 * The report_fcn field is omitted, as including it would require us to
45 * make H5C_t structure public.
46 *
47 * The dirty_bytes_threshold field does not appear in H5C_auto_size_ctl_t,
48 * as synchronization between caches on different processes is handled at
49 * the H5AC level, not at the level of H5C. Note however that there is
50 * considerable interaction between this value and the other fields in this
51 * structure.
52 *
53 * Similarly, the open_trace_file, close_trace_file, and trace_file_name
54 * fields do not appear in H5C_auto_size_ctl_t, as most trace file
55 * issues are handled at the H5AC level. The one exception is storage of
56 * the pointer to the trace file, which is handled by H5C.
57 *
58 * The structure is in H5ACpublic.h as we may wish to allow different
59 * configuration options for metadata and raw data caches.
60 *
61 * The fields of the structure are discussed individually below:
62 *
63 * version: Integer field containing the version number of this version
64 * of the H5AC_cache_config_t structure. Any instance of
65 * H5AC_cache_config_t passed to the cache must have a known
66 * version number, or an error will be flagged.
67 *
68 * rpt_fcn_enabled: Boolean field used to enable and disable the default
69 * reporting function. This function is invoked every time the
70 * automatic cache resize code is run, and reports on its activities.
71 *
72 * This is a debugging function, and should normally be turned off.
73 *
74 * open_trace_file: Boolean field indicating whether the trace_file_name
75 * field should be used to open a trace file for the cache.
76 *
77 * *** DEPRECATED *** Use H5Fstart/stop logging functions instead
78 *
79 * The trace file is a debugging feature that allow the capture of
80 * top level metadata cache requests for purposes of debugging and/or
81 * optimization. This field should normally be set to FALSE, as
82 * trace file collection imposes considerable overhead.
83 *
84 * This field should only be set to TRUE when the trace_file_name
85 * contains the full path of the desired trace file, and either
86 * there is no open trace file on the cache, or the close_trace_file
87 * field is also TRUE.
88 *
89 * close_trace_file: Boolean field indicating whether the current trace
90 * file (if any) should be closed.
91 *
92 * *** DEPRECATED *** Use H5Fstart/stop logging functions instead
93 *
94 * See the above comments on the open_trace_file field. This field
95 * should be set to FALSE unless there is an open trace file on the
96 * cache that you wish to close.
97 *
98 * trace_file_name: Full path of the trace file to be opened if the
99 * open_trace_file field is TRUE.
100 *
101 * *** DEPRECATED *** Use H5Fstart/stop logging functions instead
102 *
103 * In the parallel case, an ascii representation of the mpi rank of
104 * the process will be appended to the file name to yield a unique
105 * trace file name for each process.
106 *
107 * The length of the path must not exceed H5AC__MAX_TRACE_FILE_NAME_LEN
108 * characters.
109 *
110 * evictions_enabled: Boolean field used to either report the current
111 * evictions enabled status of the cache, or to set the cache's
112 * evictions enabled status.
113 *
114 * In general, the metadata cache should always be allowed to
115 * evict entries. However, in some cases it is advantageous to
116 * disable evictions briefly, and thereby postpone metadata
117 * writes. However, this must be done with care, as the cache
118 * can grow quickly. If you do this, re-enable evictions as
119 * soon as possible and monitor cache size.
120 *
121 * At present, evictions can only be disabled if automatic
122 * cache resizing is also disabled (that is, ( incr_mode ==
123 * H5C_incr__off ) && ( decr_mode == H5C_decr__off )). There
124 * is no logical reason why this should be so, but it simplifies
125 * implementation and testing, and I can't think of any reason
126 * why it would be desirable. If you can think of one, I'll
127 * revisit the issue.
128 *
129 * set_initial_size: Boolean flag indicating whether the size of the
130 * initial size of the cache is to be set to the value given in
131 * the initial_size field. If set_initial_size is FALSE, the
132 * initial_size field is ignored.
133 *
134 * initial_size: If enabled, this field contain the size the cache is
135 * to be set to upon receipt of this structure. Needless to say,
136 * initial_size must lie in the closed interval [min_size, max_size].
137 *
138 * min_clean_fraction: double in the range 0 to 1 indicating the fraction
139 * of the cache that is to be kept clean. This field is only used
140 * in parallel mode. Typical values are 0.1 to 0.5.
141 *
142 * max_size: Maximum size to which the cache can be adjusted. The
143 * supplied value must fall in the closed interval
144 * [MIN_MAX_CACHE_SIZE, MAX_MAX_CACHE_SIZE]. Also, max_size must
145 * be greater than or equal to min_size.
146 *
147 * min_size: Minimum size to which the cache can be adjusted. The
148 * supplied value must fall in the closed interval
149 * [H5C__MIN_MAX_CACHE_SIZE, H5C__MAX_MAX_CACHE_SIZE]. Also, min_size
150 * must be less than or equal to max_size.
151 *
152 * epoch_length: Number of accesses on the cache over which to collect
153 * hit rate stats before running the automatic cache resize code,
154 * if it is enabled.
155 *
156 * At the end of an epoch, we discard prior hit rate data and start
157 * collecting afresh. The epoch_length must lie in the closed
158 * interval [H5C__MIN_AR_EPOCH_LENGTH, H5C__MAX_AR_EPOCH_LENGTH].
159 *
160 *
161 * Cache size increase control fields:
162 *
163 * incr_mode: Instance of the H5C_cache_incr_mode enumerated type whose
164 * value indicates how we determine whether the cache size should be
165 * increased. At present there are two possible values:
166 *
167 * H5C_incr__off: Don't attempt to increase the size of the cache
168 * automatically.
169 *
170 * When this increment mode is selected, the remaining fields
171 * in the cache size increase section ar ignored.
172 *
173 * H5C_incr__threshold: Attempt to increase the size of the cache
174 * whenever the average hit rate over the last epoch drops
175 * below the value supplied in the lower_hr_threshold
176 * field.
177 *
178 * Note that this attempt will fail if the cache is already
179 * at its maximum size, or if the cache is not already using
180 * all available space.
181 *
182 * Note that you must set decr_mode to H5C_incr__off if you
183 * disable metadata cache entry evictions.
184 *
185 * lower_hr_threshold: Lower hit rate threshold. If the increment mode
186 * (incr_mode) is H5C_incr__threshold and the hit rate drops below the
187 * value supplied in this field in an epoch, increment the cache size by
188 * size_increment. Note that cache size may not be incremented above
189 * max_size, and that the increment may be further restricted by the
190 * max_increment field if it is enabled.
191 *
192 * When enabled, this field must contain a value in the range [0.0, 1.0].
193 * Depending on the incr_mode selected, it may also have to be less than
194 * upper_hr_threshold.
195 *
196 * increment: Double containing the multiplier used to derive the new
197 * cache size from the old if a cache size increment is triggered.
198 * The increment must be greater than 1.0, and should not exceed 2.0.
199 *
200 * The new cache size is obtained my multiplying the current max cache
201 * size by the increment, and then clamping to max_size and to stay
202 * within the max_increment as necessary.
203 *
204 * apply_max_increment: Boolean flag indicating whether the max_increment
205 * field should be used to limit the maximum cache size increment.
206 *
207 * max_increment: If enabled by the apply_max_increment field described
208 * above, this field contains the maximum number of bytes by which the
209 * cache size can be increased in a single re-size.
210 *
211 * flash_incr_mode: Instance of the H5C_cache_flash_incr_mode enumerated
212 * type whose value indicates whether and by which algorithm we should
213 * make flash increases in the size of the cache to accommodate insertion
214 * of large entries and large increases in the size of a single entry.
215 *
216 * The addition of the flash increment mode was occasioned by performance
217 * problems that appear when a local heap is increased to a size in excess
218 * of the current cache size. While the existing re-size code dealt with
219 * this eventually, performance was very bad for the remainder of the
220 * epoch.
221 *
222 * At present, there are two possible values for the flash_incr_mode:
223 *
224 * H5C_flash_incr__off: Don't perform flash increases in the size of
225 * the cache.
226 *
227 * H5C_flash_incr__add_space: Let x be either the size of a newly
228 * newly inserted entry, or the number of bytes by which the
229 * size of an existing entry has been increased.
230 *
231 * If
232 * x > flash_threshold * current max cache size,
233 *
234 * increase the current maximum cache size by x * flash_multiple
235 * less any free space in the cache, and star a new epoch. For
236 * now at least, pay no attention to the maximum increment.
237 *
238 * In both of the above cases, the flash increment pays no attention to
239 * the maximum increment (at least in this first incarnation), but DOES
240 * stay within max_size.
241 *
242 * With a little thought, it should be obvious that the above flash
243 * cache size increase algorithm is not sufficient for all circumstances
244 * -- for example, suppose the user round robins through
245 * (1/flash_threshold) +1 groups, adding one data set to each on each
246 * pass. Then all will increase in size at about the same time, requiring
247 * the max cache size to at least double to maintain acceptable
248 * performance, however the above flash increment algorithm will not be
249 * triggered.
250 *
251 * Hopefully, the add space algorithms detailed above will be sufficient
252 * for the performance problems encountered to date. However, we should
253 * expect to revisit the issue.
254 *
255 * flash_multiple: Double containing the multiple described above in the
256 * H5C_flash_incr__add_space section of the discussion of the
257 * flash_incr_mode section. This field is ignored unless flash_incr_mode
258 * is H5C_flash_incr__add_space.
259 *
260 * flash_threshold: Double containing the factor by which current max cache
261 * size is multiplied to obtain the size threshold for the add_space flash
262 * increment algorithm. The field is ignored unless flash_incr_mode is
263 * H5C_flash_incr__add_space.
264 *
265 *
266 * Cache size decrease control fields:
267 *
268 * decr_mode: Instance of the H5C_cache_decr_mode enumerated type whose
269 * value indicates how we determine whether the cache size should be
270 * decreased. At present there are four possibilities.
271 *
272 * H5C_decr__off: Don't attempt to decrease the size of the cache
273 * automatically.
274 *
275 * When this increment mode is selected, the remaining fields
276 * in the cache size decrease section are ignored.
277 *
278 * H5C_decr__threshold: Attempt to decrease the size of the cache
279 * whenever the average hit rate over the last epoch rises
280 * above the value supplied in the upper_hr_threshold
281 * field.
282 *
283 * H5C_decr__age_out: At the end of each epoch, search the cache for
284 * entries that have not been accessed for at least the number
285 * of epochs specified in the epochs_before_eviction field, and
286 * evict these entries. Conceptually, the maximum cache size
287 * is then decreased to match the new actual cache size. However,
288 * this reduction may be modified by the min_size, the
289 * max_decrement, and/or the empty_reserve.
290 *
291 * H5C_decr__age_out_with_threshold: Same as age_out, but we only
292 * attempt to reduce the cache size when the hit rate observed
293 * over the last epoch exceeds the value provided in the
294 * upper_hr_threshold field.
295 *
296 * Note that you must set decr_mode to H5C_decr__off if you
297 * disable metadata cache entry evictions.
298 *
299 * upper_hr_threshold: Upper hit rate threshold. The use of this field
300 * varies according to the current decr_mode:
301 *
302 * H5C_decr__off or H5C_decr__age_out: The value of this field is
303 * ignored.
304 *
305 * H5C_decr__threshold: If the hit rate exceeds this threshold in any
306 * epoch, attempt to decrement the cache size by size_decrement.
307 *
308 * Note that cache size may not be decremented below min_size.
309 *
310 * Note also that if the upper_threshold is 1.0, the cache size
311 * will never be reduced.
312 *
313 * H5C_decr__age_out_with_threshold: If the hit rate exceeds this
314 * threshold in any epoch, attempt to reduce the cache size
315 * by evicting entries that have not been accessed for more
316 * than the specified number of epochs.
317 *
318 * decrement: This field is only used when the decr_mode is
319 * H5C_decr__threshold.
320 *
321 * The field is a double containing the multiplier used to derive the
322 * new cache size from the old if a cache size decrement is triggered.
323 * The decrement must be in the range 0.0 (in which case the cache will
324 * try to contract to its minimum size) to 1.0 (in which case the
325 * cache will never shrink).
326 *
327 * apply_max_decrement: Boolean flag used to determine whether decrements
328 * in cache size are to be limited by the max_decrement field.
329 *
330 * max_decrement: Maximum number of bytes by which the cache size can be
331 * decreased in a single re-size. Note that decrements may also be
332 * restricted by the min_size of the cache, and (in age out modes) by
333 * the empty_reserve field.
334 *
335 * epochs_before_eviction: Integer field used in H5C_decr__age_out and
336 * H5C_decr__age_out_with_threshold decrement modes.
337 *
338 * This field contains the number of epochs an entry must remain
339 * unaccessed before it is evicted in an attempt to reduce the
340 * cache size. If applicable, this field must lie in the range
341 * [1, H5C__MAX_EPOCH_MARKERS].
342 *
343 * apply_empty_reserve: Boolean field controlling whether the empty_reserve
344 * field is to be used in computing the new cache size when the
345 * decr_mode is H5C_decr__age_out or H5C_decr__age_out_with_threshold.
346 *
347 * empty_reserve: To avoid a constant racheting down of cache size by small
348 * amounts in the H5C_decr__age_out and H5C_decr__age_out_with_threshold
349 * modes, this field allows one to require that any cache size
350 * reductions leave the specified fraction of unused space in the cache.
351 *
352 * The value of this field must be in the range [0.0, 1.0]. I would
353 * expect typical values to be in the range of 0.01 to 0.1.
354 *
355 *
356 * Parallel Configuration Fields:
357 *
358 * In PHDF5, all operations that modify metadata must be executed collectively.
359 *
360 * We used to think that this was enough to ensure consistency across the
361 * metadata caches, but since we allow processes to read metadata individually,
362 * the order of dirty entries in the LRU list can vary across processes,
363 * which can result in inconsistencies between the caches.
364 *
365 * PHDF5 uses several strategies to prevent such inconsistencies in metadata,
366 * all of which use the fact that the same stream of dirty metadata is seen
367 * by all processes for purposes of synchronization. This is done by
368 * having each process count the number of bytes of dirty metadata generated,
369 * and then running a "sync point" whenever this count exceeds a user
370 * specified threshold (see dirty_bytes_threshold below).
371 *
372 * The current metadata write strategy is indicated by the
373 * metadata_write_strategy field. The possible values of this field, along
374 * with the associated metadata write strategies are discussed below.
375 *
376 * dirty_bytes_threshold: Threshold of dirty byte creation used to
377 * synchronize updates between caches. (See above for outline and
378 * motivation.)
379 *
380 * This value MUST be consistent across all processes accessing the
381 * file. This field is ignored unless HDF5 has been compiled for
382 * parallel.
383 *
384 * metadata_write_strategy: Integer field containing a code indicating the
385 * desired metadata write strategy. The valid values of this field
386 * are enumerated and discussed below:
387 *
388 *
389 * H5AC_METADATA_WRITE_STRATEGY__PROCESS_0_ONLY:
390 *
391 * When metadata_write_strategy is set to this value, only process
392 * zero is allowed to write dirty metadata to disk. All other
393 * processes must retain dirty metadata until they are informed at
394 * a sync point that the dirty metadata in question has been written
395 * to disk.
396 *
397 * When the sync point is reached (or when there is a user generated
398 * flush), process zero flushes sufficient entries to bring it into
399 * compliance with its min clean size (or flushes all dirty entries in
400 * the case of a user generated flush), broad casts the list of
401 * entries just cleaned to all the other processes, and then exits
402 * the sync point.
403 *
404 * Upon receipt of the broadcast, the other processes mark the indicated
405 * entries as clean, and leave the sync point as well.
406 *
407 *
408 * H5AC_METADATA_WRITE_STRATEGY__DISTRIBUTED:
409 *
410 * In the distributed metadata write strategy, process zero still makes
411 * the decisions as to what entries should be flushed, but the actual
412 * flushes are distributed across the processes in the computation to
413 * the extent possible.
414 *
415 * In this strategy, when a sync point is triggered (either by dirty
416 * metadata creation or manual flush), all processes enter a barrier.
417 *
418 * On the other side of the barrier, process 0 constructs an ordered
419 * list of the entries to be flushed, and then broadcasts this list
420 * to the caches in all the processes.
421 *
422 * All processes then scan the list of entries to be flushed, flushing
423 * some, and marking the rest as clean. The algorithm for this purpose
424 * ensures that each entry in the list is flushed exactly once, and
425 * all are marked clean in each cache.
426 *
427 * Note that in the case of a flush of the cache, no message passing
428 * is necessary, as all processes have the same list of dirty entries,
429 * and all of these entries must be flushed. Thus in this case it is
430 * sufficient for each process to sort its list of dirty entries after
431 * leaving the initial barrier, and use this list as if it had been
432 * received from process zero.
433 *
434 * To avoid possible messages from the past/future, all caches must
435 * wait until all caches are done before leaving the sync point.
436 *
437 ****************************************************************************/
