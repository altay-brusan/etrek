\+\#define LZMA\+\_\+\+CONCATENATED~UINT32\+\_\+C(0x08)}

This flag enables decoding of concatenated files with file formats that allow concatenating compressed files as is. From the formats currently supported by liblzma, only the .xz and .lz formats allow concatenated files. Concatenated files are not allowed with the legacy .lzma format.

This flag also affects the usage of the \textquotesingle{}action\textquotesingle{} argument for lzma\+\_\+code(). When LZMA\+\_\+\+CONCATENATED is used, lzma\+\_\+code() won\textquotesingle{}t return LZMA\+\_\+\+STREAM\+\_\+\+END unless LZMA\+\_\+\+FINISH is used as \textquotesingle{}action\textquotesingle{}. Thus, the application has to set LZMA\+\_\+\+FINISH in the same way as it does when encoding.

If LZMA\+\_\+\+CONCATENATED is not used, the decoders still accept LZMA\+\_\+\+FINISH as \textquotesingle{}action\textquotesingle{} for lzma\+\_\+code(), but the usage of LZMA\+\_\+\+FINISH isn\textquotesingle{}t required. \Hypertarget{container_8h_aa1f469ed3d4b2eaf12f8081657efc9d5}\index{container.h@{container.h}!LZMA\_FAIL\_FAST@{LZMA\_FAIL\_FAST}}

\doxysubsubsection{\texorpdfstring{LZMA\_FAIL\_FAST}{LZMA\_FAIL\_FAST}}
{\footnotesize\ttfamily \label{container_8h_aa1f469ed3d4b2eaf12f8081657efc9d5} 
\+\#define LZMA\+\_\+\+FAIL\+\_\+\+FAST~UINT32\+\_\+C(0x20)}

This flag makes the threaded decoder report errors (like LZMA\+\_\+\+DATA\+\_\+\+ERROR) as soon as they are detected. This saves time when the application has no interest in a partially decompressed truncated or corrupt file. Note that due to timing randomness, if the same truncated or corrupt input is decompressed multiple times with this flag, a different amount of output may be produced by different runs, and even the error code might vary.

When using LZMA\+\_\+\+FAIL\+\_\+\+FAST, it is recommended to use LZMA\+\_\+\+FINISH to tell the decoder when no more input will be coming because it can help fast detection and reporting of truncated files. Note that in this situation truncated files might be diagnosed with LZMA\+\_\+\+DATA\+\_\+\+ERROR instead of LZMA\+\_\+\+OK or LZMA\+\_\+\+BUF\+\_\+\+ERROR!

Without this flag the threaded decoder will provide as much output as possible at first and then report the pending error. This default behavior matches the single-\/threaded decoder and provides repeatable behavior with truncated or corrupt input. There are a few special cases where the behavior can still differ like memory allocation failures (LZMA\+\_\+\+MEM\+\_\+\+ERROR).

Single-\/threaded decoders currently ignore this flag.

Support for this flag was added in liblzma 5.\+3.\+3alpha. Note that in older versions this flag isn\textquotesingle{}t supported (LZMA\+\_\+\+OPTIONS\+\_\+\+ERROR) even by functions that ignore this flag in newer liblzma versions. \Hypertarget{container_8h_a1289925ae1c63a8e86f69f3657118a4d}\index{container.h@{container.h}!LZMA\_IGNORE\_CHECK@{LZMA\_IGNORE\_CHECK}}

\+\#define LZMA\+\_\+\+IGNORE\+\_\+\+CHECK~UINT32\+\_\+C(0x10)}

This flag makes lzma\+\_\+code() not calculate and verify the integrity check of the compressed data in .xz files. This means that invalid integrity check values won\textquotesingle{}t be detected and LZMA\+\_\+\+DATA\+\_\+\+ERROR won\textquotesingle{}t be returned in such cases.

This flag only affects the checks of the compressed data itself; the CRC32 values in the .xz headers will still be verified normally.

Don\textquotesingle{}t use this flag unless you know what you are doing. Possible reasons to use this flag:\+


\begin{DoxyItemize}
\item Trying to recover data from a corrupt .xz file.
\item Speeding up decompression, which matters mostly with SHA-\/256 or with files that have compressed extremely well. It\textquotesingle{}s recommended to not use this flag for this purpose unless the file integrity is verified externally in some other way.
\end{DoxyItemize}

\doxylink{requirements_The}{The} Micro\+LZMA format is a raw LZMA stream whose first byte (always 0x00) has been replaced with bitwise-\/negation of the LZMA properties (lc/\+lp/\+pb). This encoding ensures that the first byte of Micro\+LZMA stream is never 0x00. There is no end of payload marker and thus the uncompressed size must be stored separately. For the best error detection the dictionary size should be stored separately as well but alternatively one may use the uncompressed size as the dictionary size when decoding.

With the Micro\+LZMA encoder, lzma\+\_\+code() behaves slightly unusually. \doxylink{requirements_The}{The} action argument must be LZMA\+\_\+\+FINISH and the return value will never be LZMA\+\_\+\+OK. Thus the encoding is always done with a single lzma\+\_\+code() after the initialization. \doxylink{requirements_The}{The} benefit of the combination of initialization function and lzma\+\_\+code() is that memory allocations can be re-\/used for better performance.

lzma\+\_\+code() will try to encode as much input as is possible to fit into the given output buffer. If not all input can be encoded, the stream will be finished without encoding all the input. \doxylink{requirements_The}{The} caller must check both input and output buffer usage after lzma\+\_\+code() (total\+\_\+in and total\+\_\+out in \doxylink{structlzma__stream}{lzma\+\_\+stream} can be convenient). Often lzma\+\_\+code() can fill the output buffer completely if there is a lot of input, but sometimes a few bytes may remain unused because the next LZMA symbol would require more space.

\doxylink{structlzma__stream_a5ff28ea4e39148723c19f59811627904}{lzma\+\_\+stream.\+avail\+\_\+out} must be at least 6. Otherwise LZMA\+\_\+\+PROG\+\_\+\+ERROR will be returned.

\doxylink{requirements_The}{The} LZMA dictionary should be reasonably low to speed up the encoder re-\/initialization. A good value is bigger than the resulting uncompressed size of most of the output chunks. For example, if output size is 4 KiB, dictionary size of 32 KiB or 64 KiB is good. If the data compresses extremely well, even 128 KiB may be useful.

\doxylink{requirements_The}{The} Micro\+LZMA format and this encoder variant were made with the EROFS file system in mind. This format may be convenient in other embedded uses too where many small streams are needed. XZ Embedded includes a decoder for this format.

Calculate output buffer size for single-\/call Stream encoder. 

When trying to compress incompressible data, the encoded size will be slightly bigger than the input data. This function calculates how much output buffer space is required to be sure that lzma\+\_\+stream\+\_\+buffer\+\_\+encode() doesn\textquotesingle{}t return LZMA\+\_\+\+BUF\+\_\+\+ERROR.

\doxylink{requirements_The}{The} calculated value is not exact, but it is guaranteed to be big enough. \doxylink{requirements_The}{The} actual maximum output space required may be slightly smaller (up to about 100 bytes). This should not be a problem in practice.

If the calculated maximum size doesn\textquotesingle{}t fit into size\+\_\+t or would make the Stream grow past LZMA\+\_\+\+VLI\+\_\+\+MAX (which should never happen in practice), zero is returned to indicate the error.

\begin{DoxyNote}{Note}
\doxylink{requirements_The}{The} limit calculated by this function applies only to single-\/call encoding. Multi-\/call encoding may (and probably will) have larger maximum expansion when encoding incompressible data. Currently there is no function to calculate the maximum expansion of multi-\/call encoding.
\end{DoxyNote}
