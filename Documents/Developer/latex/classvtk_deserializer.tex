{\footnotesize\ttfamily \label{classvtk_deserializer_af2009f1482267c5310d3ca6f92e25d38} 
\doxymbox{\hyperlink{classvtk_object_base}{vtk\+Object\+Base}} \texorpdfstring{$\ast$}{*} vtk\+Deserializer::\+\+Construct\+Object (\begin{DoxyParamCaption}\item[{const std::\+string \&}]{class\+Name}{, }\item[{const std::\+vector$<$ std::\+string $>$ \&}]{super\+Class\+Names}{}\end{DoxyParamCaption})}

Constructs an object of type {\ttfamily class\+Name}.

If a constructor is not found for {\ttfamily class\+Name}, the {\ttfamily Get\+Constructor} walks through each item in {\ttfamily super\+Class\+Names} and attempts to construct an instance of that type. This is useful when the VTK build of the serializer side and the deserializer side are on entirely different platforms by taking advantage of the object factory mechanism.

Example of usefulness of {\ttfamily super\+Class\+Names}:\+

Let\textquotesingle{}s suppose in a Windows VTK application, the {\ttfamily \doxylink{classvtk_serializer}{vtk\+Serializer}} serialized an instance of {\ttfamily \doxylink{classvtk_win32_render_window_interactor}{vtk\+Win32\+Render\+Window\+Interactor}} into json which was then transferred over the network to a mac\+OS machine. Over there, seeing that the state refers to the {\ttfamily \doxylink{classvtk_win32_render_window_interactor}{vtk\+Win32\+Render\+Window\+Interactor}} class the {\ttfamily \doxylink{classvtk_deserializer}{vtk\+Deserializer}} will attempt to find a constructor for win32 class and fail. It then checks if the super class (here {\ttfamily \doxylink{classvtk_render_window_interactor}{vtk\+Render\+Window\+Interactor}}) has a constructor and constructs a new instance of that type. Due to the object factory mechanism, the mac\+OS build of VTK constructs a {\ttfamily vtk\+Cocoa\+Render\+Window\+Interactor} and it all works as expected! \Hypertarget{classvtk_deserializer_ac248d152702788223796bd938571c727}\index{vtkDeserializer@{vtkDeserializer}!DeserializeJSON@{DeserializeJSON}}
