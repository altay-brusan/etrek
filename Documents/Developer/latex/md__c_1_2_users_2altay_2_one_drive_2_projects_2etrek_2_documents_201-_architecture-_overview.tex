This document describes the software architecture of E-\/\+TREK, a medical imaging Digital Radiography (DR) workstation application. \doxylink{requirements_The}{The} architecture is presented using the 4+1 View Model, which addresses the concerns of different stakeholders through five complementary views:\+ Logical, Development, Process, Physical, and Scenarios.\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md229}{}\doxysubsection{\texorpdfstring{1.\+2 Scope}{1.\+2 Scope}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md229}
E-\/\+TREK is designed as a generic workstation software for medical X-\/ray imaging systems. \doxylink{requirements_The}{The} software integrates with hospital information systems through DICOM Modality Worklist (MWL), controls X-\/ray hardware including generators and detectors, and provides comprehensive image viewing capabilities.

{\bfseries{\doxylink{requirements_The}{The} system supports multiple simultaneous Modality Worklist connections}}, allowing integration with different RIS (Radiology Information System) providers. Each MWL connection can be independently configured with its own DICOM tag mappings, transfer syntaxes, and query parameters. This flexibility enables healthcare facilities to connect to multiple scheduling systems or migrate between providers without software modifications.\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md230}{}\doxysubsection{\texorpdfstring{1.\+3 Definitions and Acronyms}{1.\+3 Definitions and Acronyms}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md230}

\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md233}{}\doxysubsection{\texorpdfstring{2.\+1 Target Hardware}{2.\+1 Target Hardware}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md233}
E-\/\+TREK is designed as a workstation software for medical X-\/ray machines. \doxylink{requirements_The}{The} software is intentionally generic and independent of any specific X-\/ray equipment manufacturer, allowing device manufacturers and system integrators to incorporate E-\/\+TREK into their products.

\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md234}{}\doxysubsection{\texorpdfstring{2.\+2 Supported Configurations}{2.\+2 Supported Configurations}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md234}
\doxylink{requirements_The}{The} device organization in E-\/\+TREK supports various X-\/ray system configurations:\+

{\bfseries{Detector Configurations:\+}}
\begin{DoxyItemize}
\item Single detector systems (standard radiography)
\item Dual detector systems (table + wall stand, or dual wall stands)
\item Line scanner detectors (for slot radiography and cephalometry)
\end{DoxyItemize}

{\bfseries{X-\/\+Ray Tube Configurations:\+}}
\begin{DoxyItemize}
\item Single tube systems
\item Dual tube systems (ceiling-\/mounted + floor-\/mounted)
\end{DoxyItemize}

{\bfseries{Imaging Techniques:\+}}
\begin{DoxyItemize}
\item Standard single-\/exposure radiography
\item Dual-\/exposure techniques (for dual-\/energy subtraction imaging)
\item Cephalography (orthodontic and ENT imaging)
\item Slot scanning /\+ Line scanning (full-\/leg, full-\/spine imaging)
\end{DoxyItemize}\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md235}{}\doxysubsection{\texorpdfstring{2.\+3 Integration Model}{2.\+3 Integration Model}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md235}
E-\/\+TREK provides a hardware abstraction layer that allows equipment manufacturers to integrate their specific hardware through well-\/defined interfaces. \doxylink{requirements_The}{The} software communicates with hardware through configurable protocols including RS-\/232, RS-\/485, CAN bus, Modbus, and Ethernet.

Before describing the architecture views, this section introduces the key design patterns and principles used throughout E-\/\+TREK.\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md238}{}\doxysubsection{\texorpdfstring{3.\+1 Model-\/\+View-\/\+Delegate Pattern}{3.\+1 Model-\/\+View-\/\+Delegate Pattern}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md238}
E-\/\+TREK uses the Model-\/\+View-\/\+Delegate (MVD) pattern, a variation of Model-\/\+View-\/\+Controller adapted for Qt applications. This pattern separates the application into three interconnected components:\+                                

{\bfseries{Benefits of MVD:\+}}
\begin{DoxyItemize}
\item Clear separation between UI and business logic
\item Views can be replaced or modified without changing business rules
\item Business logic can be tested independently of the UI
\item Multiple views can share the same delegate logic
\end{DoxyItemize}\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md239}{}\doxysubsection{\texorpdfstring{3.\+2 Builder Pattern}{3.\+2 Builder Pattern}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md239}
E-\/\+TREK uses the Builder pattern to construct complex objects (pages with their delegates and dependencies). Builders encapsulate the construction logic, making it easier to create properly configured objects.

\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md240}{}\doxysubsection{\texorpdfstring{3.\+3 Dependency Injection}{3.\+3 Dependency Injection}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md240}
Dependency Injection (DI) is a technique where objects receive their dependencies from external sources rather than creating them internally. In E-\/\+TREK, the {\ttfamily \doxylink{struct_delegate_parameter}{Delegate\+Parameter}} structure serves as a simple dependency injection container.

\hypertarget{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md241}{}\doxysubsection{\texorpdfstring{3.\+4 Repository Pattern}{3.\+4 Repository Pattern}}\label{md__c_1_2_users_2altay_2_one_drive_2_projects_2etrek_2_documents_201-_architecture-_overview_autotoc_md241}
\doxylink{requirements_The}{The} Repository pattern abstracts data access behind a collection-\/like interface. Components work with repositories rather than directly with the database, making the code more testable and the data layer replaceable.
