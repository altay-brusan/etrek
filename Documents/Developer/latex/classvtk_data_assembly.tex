\doxysubsection{Detailed Description}
hierarchical representation to use with \doxylink{classvtk_partitioned_data_set_collection}{vtk\+Partitioned\+Data\+Set\+Collection} 

\doxylink{classvtk_data_assembly}{vtk\+Data\+Assembly} is a mechanism to represent hierarchical organization of items (or \doxylink{classvtk_partitioned_data_set}{vtk\+Partitioned\+Data\+Set} instances) in a \doxylink{classvtk_partitioned_data_set_collection}{vtk\+Partitioned\+Data\+Set\+Collection}. \doxylink{classvtk_partitioned_data_set_collection}{vtk\+Partitioned\+Data\+Set\+Collection} is similar to a \doxylink{classvtk_multi_block_data_set}{vtk\+Multi\+Block\+Data\+Set} since it provides a means for putting together multiple non-\/composite datasets. However, \doxylink{classvtk_partitioned_data_set_collection}{vtk\+Partitioned\+Data\+Set\+Collection} itself doesn\textquotesingle{}t provide any mechanism to define relationships between items in the collections. That is done using \doxylink{classvtk_data_assembly}{vtk\+Data\+Assembly}.\hypertarget{classvtk_data_assembly_Overview}{}\doxysubsection{\texorpdfstring{Overview}{Overview}}\label{classvtk_data_assembly_Overview}
At its core, \doxylink{classvtk_data_assembly}{vtk\+Data\+Assembly} is simply a tree of nodes starting with the root node. Each node has a unique id and a string name (names need not be unique). On initialization with {\ttfamily \doxylink{classvtk_data_assembly_abc096c396329b2dcb224f5bb13ec058d}{vtk\+Data\+Assembly::\+\+Initialize}}, an empty tree with a root node is created. \doxylink{requirements_The}{The} root node\textquotesingle{}s id and name can be obtained using {\ttfamily \doxylink{classvtk_data_assembly_a06b54ed2dd8299dce803c5b217c1f6ca}{vtk\+Data\+Assembly::\+\+Get\+Root\+Node}} and {\ttfamily vtk\+Data\+Assembly::\+\+Get\+Root\+Node\+Name}. \doxylink{requirements_The}{The} root node\textquotesingle{}s id is fixed (\doxylink{classvtk_data_assembly_a06b54ed2dd8299dce803c5b217c1f6ca}{vtk\+Data\+Assembly::\+\+Get\+Root\+Node}), however the name can be changed using {\ttfamily \doxylink{classvtk_data_assembly_ac60ac59ad6b35ddb8a2d5b1ef02c8d71}{vtk\+Data\+Assembly::\+\+Set\+Root\+Node\+Name}}.

Child nodes can be added using {\ttfamily \doxylink{classvtk_data_assembly_a8f117b8b0ee8541a92fb4e9c0c84e50d}{vtk\+Data\+Assembly::\+\+Add\+Node}} or {\ttfamily \doxylink{classvtk_data_assembly_ad1284b8ce4134b09050bc20a37b255c5}{vtk\+Data\+Assembly::\+\+Add\+Nodes}}, each of which returns the ids for every child node added. A non-\/root node can be removed using {\ttfamily \doxylink{classvtk_data_assembly_adae3516aa1b10872cad617cf9012bdaa}{vtk\+Data\+Assembly::\+\+Remove\+Node}}.

Each node in the tree (including the root node) can have associated dataset indices. For a \doxylink{classvtk_data_assembly}{vtk\+Data\+Assembly} associated with a \doxylink{classvtk_partitioned_data_set_collection}{vtk\+Partitioned\+Data\+Set\+Collection}, these indices refer to the item index, or partitioned-\/dataset-\/index for items in the collection. Dataset indices can be specified using {\ttfamily \doxylink{classvtk_data_assembly_a4e4a4b1a9ac5e7788aaf9a986618a269}{vtk\+Data\+Assembly::\+\+Add\+Data\+Set\+Index}}, {\ttfamily \doxylink{classvtk_data_assembly_a90aa56d6302d9bec063de4f66d5f1b00}{vtk\+Data\+Assembly::\+\+Add\+Data\+Set\+Indices}} and removed using {\ttfamily \doxylink{classvtk_data_assembly_acc30af82e47ee70d4f6f2b4d81e7ff52}{vtk\+Data\+Assembly::\+\+Remove\+Data\+Set\+Index}}, {\ttfamily \doxylink{classvtk_data_assembly_ad5fa34b108f2badeefb0ddfdf688ad0c}{vtk\+Data\+Assembly::\+\+Remove\+All\+Data\+Set\+Indices}}. {\ttfamily \doxylink{classvtk_data_assembly_a62a06760e3d52747f9ee840cf7f7ecfb}{vtk\+Data\+Assembly::\+\+Get\+Data\+Set\+Indices}} provides a mechanism to get the database indices associated with a node, and optionally, the entire subtree rooted at the chosen node.\hypertarget{classvtk_data_assembly_Searching}{}\doxysubsection{\texorpdfstring{Searching}{Searching}}\label{classvtk_data_assembly_Searching}
Each node in the \doxylink{classvtk_data_assembly}{vtk\+Data\+Assembly} is assigned a unique id. {\ttfamily \doxylink{classvtk_data_assembly_a636a5a095e9a9735998520bb3b6e5404}{vtk\+Data\+Assembly::\+\+Find\+First\+Node\+With\+Name}} and {\ttfamily \doxylink{classvtk_data_assembly_a0b6a0f8e6d33bc41dabe162a42ccbf3d}{vtk\+Data\+Assembly::\+\+Find\+Nodes\+With\+Name}} can be used to get the id(s) for node(s) with given name.

{\ttfamily \doxylink{classvtk_data_assembly_a553a038904b9d37223ad92012f769434}{vtk\+Data\+Assembly::\+\+Select\+Nodes}} provides a more flexible mechanism to find nodes using name-\/based queries. Section \doxysectlink{classvtk_data_assembly_DataAssemblyPathQueries}{Supported Path Queries}{1} covers supported queries.\hypertarget{classvtk_data_assembly_Traversal}{}\doxysubsection{\texorpdfstring{Traversal}{Traversal}}\label{classvtk_data_assembly_Traversal}
{\ttfamily \doxylink{classvtk_data_assembly_visitor}{vtk\+Data\+Assembly\+Visitor}} defines a visitor API. An instance of a concretized {\ttfamily \doxylink{classvtk_data_assembly_visitor}{vtk\+Data\+Assembly\+Visitor}} subclass can be passed to {\ttfamily \doxylink{classvtk_data_assembly_aaf055b745500c5d291d09242ea91b51a}{vtk\+Data\+Assembly::\+\+Visit}} to traverse the data-\/assembly hierarchy either in depth-\/first or breadth-\/first order.\hypertarget{classvtk_data_assembly_DataAssemblyPathQueries}{}\doxysubsection{\texorpdfstring{Supported Path Queries}{Supported Path Queries}}\label{classvtk_data_assembly_DataAssemblyPathQueries}
{\ttfamily \doxylink{classvtk_data_assembly_a553a038904b9d37223ad92012f769434}{vtk\+Data\+Assembly::\+\+Select\+Nodes}} can be used find nodes that match the specified query (or queries) using XPath 1.\+0 syntax.

For example:\+


\begin{DoxyItemize}
\item \textquotesingle{}/\+\textquotesingle{} is used as the path separator. If a node name has a {\ttfamily /\+} it must be escaped using {\ttfamily \textbackslash{}\textbackslash{}} in the query. Note, escaping is not necessary when using {\ttfamily \doxylink{classvtk_data_assembly_aa5a87449d0a263b5bd4c29f96b216a3e}{Set\+Node\+Name}}/\+{\ttfamily Get\+Node\+Name}.
\item \textquotesingle{}/\+\textquotesingle{} selects the root node.
\item \textquotesingle{}/\+nodename\textquotesingle{} selects all child nodes of the root with the name \textquotesingle{}nodename\textquotesingle{}.
\item \textquotesingle{}/\+/\+nodename\textquotesingle{} selects all nodes with \textquotesingle{}nodename\textquotesingle{} that are descendants of the root; thus, this this will traverse the entire tree.
\item \textquotesingle{}/\+nodename/\+\textquotesingle{} selects all child nodes of all nodes named \textquotesingle{}nodename\textquotesingle{} under the root; thus, ending a query with \textquotesingle{}/\+\textquotesingle{} selects the children of the found nodes rather than the nodes themselves.
\item \textquotesingle{}/\+nodename1/\+nodename2\textquotesingle{} selects all nodes named \textquotesingle{}nodename2\textquotesingle{} which are children of nodes with name \textquotesingle{}nodename1\textquotesingle{} that are themselves children of the root node.
\item \textquotesingle{}/\+/\+nodename1/\+nodename2\textquotesingle{} finds all nodes in the tree named \textquotesingle{}nodename1\textquotesingle{} and then selects all children of these found nodes that are named \textquotesingle{}nodename2\textquotesingle{}.
\end{DoxyItemize}\hypertarget{classvtk_data_assembly_Applications}{}\doxysubsection{\texorpdfstring{Applications}{Applications}}\label{classvtk_data_assembly_Applications}
\doxylink{requirements_The}{The} separation of dataset storage (\doxylink{classvtk_partitioned_data_set_collection}{vtk\+Partitioned\+Data\+Set\+Collection}) and organization (\doxylink{classvtk_data_assembly}{vtk\+Data\+Assembly}) enables development of algorithms that can expose APIs that are not tightly coupled to dataset storage. Together, \doxylink{classvtk_partitioned_data_set_collection}{vtk\+Partitioned\+Data\+Set\+Collection} and \doxylink{classvtk_data_assembly}{vtk\+Data\+Assembly} can be thought of as a different way of organizing data that was previously organized as a \doxylink{classvtk_multi_block_data_set}{vtk\+Multi\+Block\+Data\+Set}. \doxylink{requirements_The}{The} advantage of the this newer approach is that filters can support specifying parameters using paths or path queries rather than composite indices. \doxylink{requirements_The}{The} composite indices suffered from the fact that they made no sense except for the specific \doxylink{classvtk_multi_block_data_set}{vtk\+Multi\+Block\+Data\+Set} they were applied too. Thus, if the filters input was changed, the composite ids rarely made any sense and needed to be updated. Paths and path queries, however, do not suffer from this issue.
