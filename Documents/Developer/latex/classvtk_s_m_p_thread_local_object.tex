\subsubsection*{template$<$typename T$>$\newline
class vtk\+SMPThread\+Local\+Object$<$ T $>$}
Thread local storage for VTK objects. 

This class essentially does the same thing as \doxylink{classvtk_s_m_p_thread_local}{vtk\+SMPThread\+Local} with 2 additional functions:\+
\begin{DoxyItemize}
\item \doxylink{classvtk_s_m_p_thread_local_object_a87025a464dcdb759ae9a7c1faee578c5}{Local()} allocates an object of the template argument type using New()
\item \doxylink{requirements_The}{The} destructor calls Delete() on all objects created with \doxylink{classvtk_s_m_p_thread_local_object_a87025a464dcdb759ae9a7c1faee578c5}{Local()}.
\end{DoxyItemize}

\begin{DoxyWarning}{Warning}
There is absolutely no guarantee to the order in which the local objects will be stored and hence the order in which they will be traversed when using iterators. You should not even assume that two \doxylink{classvtk_s_m_p_thread_local}{vtk\+SMPThread\+Local} populated in the same parallel section will be populated in the same order. For example, consider the following \begin{DoxyVerb}* vtkSMPThreadLocal<int> Foo;
* vtkSMPThreadLocal<int> Bar;
* class AFunctor
* {
*    void Initialize() const
*    {
*      int& foo = Foo.Local();
*      int& bar = Bar.Local();
*      foo = random();
*      bar = foo;
*    }
*
* @warning
*    void operator()(vtkIdType, vtkIdType)
*    {}
*    void Finalize()
*    {}
* };
*
* @warning
* AFunctor functor;
* vtkSMPTools::For(0, 100000, functor);
*
* @warning
* vtkSMPThreadLocal<int>::iterator itr1 = Foo.begin();
* vtkSMPThreadLocal<int>::iterator itr2 = Bar.begin();
* while (itr1 != Foo.end())
* {
*   assert(*itr1 == *itr2);
*   ++itr1; ++itr2;
* }
* \end{DoxyVerb}


It is possible and likely that the assert() will fail using the TBB backend. So if you need to store values related to each other and iterate over them together, use a struct or class to group them together and use a thread local of that class.
\end{DoxyWarning}
