typedef struct lzma\+\_\+index\+\_\+s \doxymbox{\hyperlink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index}}}



Opaque data type to hold the Index(es) and other information. 

\doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index} often holds just one .xz Index and possibly the Stream Flags of the same Stream and size of the Stream Padding field. However, multiple lzma\+\_\+indexes can be concatenated with lzma\+\_\+index\+\_\+cat() and then there may be information about multiple Streams in the same \doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index}.

Notes about thread safety:\+ Only one thread may modify \doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index} at a time. All functions that take non-\/const pointer to \doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index} modify it. As long as no thread is modifying the \doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index}, getting information from the same \doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index} can be done from multiple threads at the same time with functions that take a const pointer to \doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index} or use \doxylink{structlzma__index__iter}{lzma\+\_\+index\+\_\+iter}. \doxylink{requirements_The}{The} same iterator must be used only by one thread at a time, of course, but there can be as many iterators for the same \doxylink{index_8h_afc18c1443b3b9aa0d146b44e8755b62e}{lzma\+\_\+index} as needed.

This decoder decodes the Stream Header, Stream Footer, Index, and Stream Padding field(s) from the input .xz file and stores the resulting combined index in \texorpdfstring{$\ast$}{*}dest\+\_\+index. This information can be used to get the uncompressed file size with lzma\+\_\+index\+\_\+uncompressed\+\_\+size(\texorpdfstring{$\ast$}{*}dest\+\_\+index) or, for example, to implement random access reading by locating the Blocks in the Streams.

To get the required information from the .xz file, lzma\+\_\+code() may ask the application to seek in the input file by returning LZMA\+\_\+\+SEEK\+\_\+\+NEEDED and having the target file position specified in \doxylink{structlzma__stream_af7c43a61f3dfeb0b9c8487b7f275054e}{lzma\+\_\+stream.\+seek\+\_\+pos}. \doxylink{requirements_The}{The} number of seeks required depends on the input file and how big buffers the application provides. When possible, the decoder will seek backward and forward in the given buffer to avoid useless seek requests. Thus, if the application provides the whole file at once, no external seeking will be required (that is, lzma\+\_\+code() won\textquotesingle{}t return LZMA\+\_\+\+SEEK\+\_\+\+NEEDED).

\doxylink{requirements_The}{The} value in \doxylink{structlzma__stream_a1a411e1755d6185756caefabc3932c7b}{lzma\+\_\+stream.\+total\+\_\+in} can be used to estimate how much data liblzma had to read to get the file information. However, due to seeking and the way total\+\_\+in is updated, the value of total\+\_\+in will be somewhat inaccurate (a little too big). Thus, total\+\_\+in is a good estimate but don\textquotesingle{}t expect to see the same exact value for the same file if you change the input buffer size or switch to a different liblzma version.
