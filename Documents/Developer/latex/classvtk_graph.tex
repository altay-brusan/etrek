\doxysubsection{Detailed Description}
Base class for graph data types. 

\doxylink{classvtk_graph}{vtk\+Graph} is the abstract base class that provides all read-\/only API for graph data types. A graph consists of a collection of vertices and a collection of edges connecting pairs of vertices. \doxylink{requirements_The}{The} \doxylink{classvtk_directed_graph}{vtk\+Directed\+Graph} subclass represents a graph whose edges have inherent order from source vertex to target vertex, while \doxylink{classvtk_undirected_graph}{vtk\+Undirected\+Graph} is a graph whose edges have no inherent ordering.

Graph vertices may be traversed in two ways. In the current implementation, all vertices are assigned consecutive ids starting at zero, so they may be traversed in a simple for loop from 0 to graph-\/\texorpdfstring{$>$}{>}\doxylink{classvtk_graph_a1acbb7b69387ec2a08956d1d9d11c679}{Get\+Number\+Of\+Vertices()} -\/ 1. You may alternately create a \doxylink{classvtk_vertex_list_iterator}{vtk\+Vertex\+List\+Iterator} and call graph-\/\texorpdfstring{$>$}{>}Get\+Vertices(it). it-\/\texorpdfstring{$>$}{>}Next() will return the id of the next vertex, while it-\/\texorpdfstring{$>$}{>}Has\+Next() indicates whether there are more vertices in the graph. This is the preferred method, since in the future graphs may support filtering or subsetting where the vertex ids may not be contiguous.

Graph edges must be traversed through iterators. To traverse all edges in a graph, create an instance of \doxylink{classvtk_edge_list_iterator}{vtk\+Edge\+List\+Iterator} and call graph-\/\texorpdfstring{$>$}{>}Get\+Edges(it). it-\/\texorpdfstring{$>$}{>}Next() returns lightweight \doxylink{structvtk_edge_type}{vtk\+Edge\+Type} structures, which contain the public fields Id, Source and Target. Id is the identifier for the edge, which may be used to look up values in associated edge data arrays. Source and Target store the ids of the source and target vertices of the edge. Note that the edge list iterator DOES NOT necessarily iterate over edges in order of ascending id. To traverse edges from wrapper code (Python, Java), use it-\/\texorpdfstring{$>$}{>}Next\+Graph\+Edge() instead of it-\/\texorpdfstring{$>$}{>}Next(). This will return a heavyweight, wrappable \doxylink{classvtk_graph_edge}{vtk\+Graph\+Edge} object, which has the same fields as \doxylink{structvtk_edge_type}{vtk\+Edge\+Type} accessible through getter methods.

To traverse all edges outgoing from a vertex, create a \doxylink{classvtk_out_edge_iterator}{vtk\+Out\+Edge\+Iterator} and call graph-\/\texorpdfstring{$>$}{>}Get\+Out\+Edges(v, it). it-\/\texorpdfstring{$>$}{>}Next() returns a lightweight \doxylink{structvtk_out_edge_type}{vtk\+Out\+Edge\+Type} containing the fields Id and Target. \doxylink{requirements_The}{The} source of the edge is always the vertex that was passed as an argument to \doxylink{classvtk_graph_aa9e590baa974a7fc0f601c8c7383fd3f}{Get\+Out\+Edges()}. Incoming edges may be similarly traversed with \doxylink{classvtk_in_edge_iterator}{vtk\+In\+Edge\+Iterator}, which returns \doxylink{structvtk_in_edge_type}{vtk\+In\+Edge\+Type} structures with Id and Source fields. Both \doxylink{classvtk_out_edge_iterator}{vtk\+Out\+Edge\+Iterator} and \doxylink{classvtk_in_edge_iterator}{vtk\+In\+Edge\+Iterator} also provide the wrapper functions Next\+Graph\+Edge() which return \doxylink{classvtk_graph_edge}{vtk\+Graph\+Edge} objects.

An additional iterator, \doxylink{classvtk_adjacent_vertex_iterator}{vtk\+Adjacent\+Vertex\+Iterator} can traverse outgoing vertices directly, instead needing to parse through edges. Initialize the iterator by calling graph-\/\texorpdfstring{$>$}{>}Get\+Adjacent\+Vertices(v, it).

\doxylink{classvtk_graph}{vtk\+Graph} has two instances of \doxylink{classvtk_data_set_attributes}{vtk\+Data\+Set\+Attributes} for associated vertex and edge data. It also has a \doxylink{classvtk_points}{vtk\+Points} instance which may store x,y,z locations for each vertex. This is populated by filters such as \doxylink{classvtk_graph_layout}{vtk\+Graph\+Layout} and \doxylink{classvtk_assign_coordinates}{vtk\+Assign\+Coordinates}.

All graph types share the same implementation, so the structure of one may be shared among multiple graphs, even graphs of different types. Structures from \doxylink{classvtk_undirected_graph}{vtk\+Undirected\+Graph} and \doxylink{classvtk_mutable_undirected_graph}{vtk\+Mutable\+Undirected\+Graph} may be shared directly. Structures from \doxylink{classvtk_directed_graph}{vtk\+Directed\+Graph}, \doxylink{classvtk_mutable_directed_graph}{vtk\+Mutable\+Directed\+Graph}, and \doxylink{classvtk_tree}{vtk\+Tree} may be shared directly with the exception that setting a structure to a tree requires that a "{}is a tree"{} test passes.

For graph types that are known to be compatible, calling \doxylink{classvtk_graph_a981281cff554790bee0bdf05fb236540}{Shallow\+Copy()} or \doxylink{classvtk_graph_aac4d6daae82193ac6c5835225677a0e1}{Deep\+Copy()} will work as expected. When the outcome of a conversion is unknown (i.\+e. setting a graph to a tree), \doxylink{classvtk_graph_a93c80d654a851b754342cc0f81a4ad28}{Checked\+Shallow\+Copy()} and \doxylink{classvtk_graph_a3733a589dd1446186715259671912b10}{Checked\+Deep\+Copy()} exist which are identical to \doxylink{classvtk_graph_a981281cff554790bee0bdf05fb236540}{Shallow\+Copy()} and \doxylink{classvtk_graph_aac4d6daae82193ac6c5835225677a0e1}{Deep\+Copy()}, except that instead of emitting an error for an incompatible structure, the function returns false. This allows you to programmatically check structure compatibility without causing error messages.

To construct a graph, use \doxylink{classvtk_mutable_directed_graph}{vtk\+Mutable\+Directed\+Graph} or \doxylink{classvtk_mutable_undirected_graph}{vtk\+Mutable\+Undirected\+Graph}. You may then use Checked\+Shallow\+Copy to set the contents of a mutable graph type into one of the non-\/mutable types \doxylink{classvtk_directed_graph}{vtk\+Directed\+Graph}, \doxylink{classvtk_undirected_graph}{vtk\+Undirected\+Graph}. To construct a tree, use \doxylink{classvtk_mutable_directed_graph}{vtk\+Mutable\+Directed\+Graph}, with directed edges which point from the parent to the child, then use Checked\+Shallow\+Copy to set the structure to a \doxylink{classvtk_tree}{vtk\+Tree}.

\begin{DoxyWarning}{Warning}
All copy operations implement copy-\/on-\/write. \doxylink{requirements_The}{The} structures are initially shared, but if one of the graphs is modified, the structure is copied so that to the user they function as if they were deep copied. This means that care must be taken if different threads are accessing different graph instances that share the same structure. Race conditions may develop if one thread is modifying the graph at the same time that another graph is copying the structure.
\end{DoxyWarning}
\begin{DoxyParagraph}{Vertex pedigree IDs:\+}
\doxylink{requirements_The}{The} vertices in a \doxylink{classvtk_graph}{vtk\+Graph} can be associated with pedigree IDs through Get\+Vertex\+Data()-\/\texorpdfstring{$>$}{>}Set\+Pedigree\+Ids. In this case, there is a 1-\/1 mapping between pedigree Ids and vertices. One can query the vertex ID based on the pedigree ID using Find\+Vertex, add new vertices by pedigree ID with Add\+Vertex, and add edges based on the pedigree IDs of the source and target vertices. For example, Add\+Edge("{}\+Here"{}, "{}\+There"{}) will find (or add) vertices with pedigree ID "{}\+Here"{} and "{}\+There"{} and then introduce an edge from "{}\+Here"{} to "{}\+There"{}.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Vertex pedigree IDs:\+}
To configure the \doxylink{classvtk_graph}{vtk\+Graph} with a pedigree ID mapping, create a \doxylink{classvtk_data_array}{vtk\+Data\+Array} that will store the pedigree IDs and set that array as the pedigree ID array for the vertices via Get\+Vertex\+Data()-\/\texorpdfstring{$>$}{>}Set\+Pedigree\+Ids().
\end{DoxyParagraph}
\begin{DoxyParagraph}{Distributed graphs:\+}
\doxylink{classvtk_graph}{vtk\+Graph} instances can be distributed across multiple machines, to allow the construction and manipulation of graphs larger than a single machine could handle. A distributed graph will typically be distributed across many different nodes within a cluster, using the Message Passing Interface (MPI) to allow those cluster nodes to communicate.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Distributed graphs:\+}
An empty \doxylink{classvtk_graph}{vtk\+Graph} can be made into a distributed graph by attaching an instance of a \doxylink{classvtk_distributed_graph_helper}{vtk\+Distributed\+Graph\+Helper} via the \doxylink{classvtk_graph_a2f06360e1a493e0de0b7bea62dbabd31}{Set\+Distributed\+Graph\+Helper()} method. To determine whether a graph is distributed or not, call \doxylink{classvtk_graph_ab2215df61a1be269863fd954264f0096}{Get\+Distributed\+Graph\+Helper()} and check whether the result is non-\/nullptr. For a distributed graph, the number of processors across which the graph is distributed can be retrieved by extracting the value for the DATA\+\_\+\+NUMBER\+\_\+\+OF\+\_\+\+PIECES key in the \doxylink{classvtk_information}{vtk\+Information} object (retrieved by Get\+Information()) associated with the graph. Similarly, the value corresponding to the DATA\+\_\+\+PIECE\+\_\+\+NUMBER key of the \doxylink{classvtk_information}{vtk\+Information} object describes which piece of the data this graph instance provides.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Distributed graphs:\+}
Distributed graphs behave somewhat differently from non-\/distributed graphs, and will require special care. In a distributed graph, each of the processors will contain a subset of the vertices in the graph. That subset of vertices can be accessed via the \doxylink{classvtk_vertex_list_iterator}{vtk\+Vertex\+List\+Iterator} produced by \doxylink{classvtk_graph_aeeed05aabf5e82e2fb934756482d9cf2}{Get\+Vertices()}. \doxylink{classvtk_graph_a1acbb7b69387ec2a08956d1d9d11c679}{Get\+Number\+Of\+Vertices()}, therefore, returns the number of vertices stored locally:\+ it does not account for vertices stored on other processors. A vertex (or edge) is identified by both the rank of its owning processor and by its index within that processor, both of which are encoded within the vtk\+Id\+Type value that describes that vertex (or edge). \doxylink{requirements_The}{The} owning processor is a value between 0 and P-\/1, where P is the number of processors across which the \doxylink{classvtk_graph}{vtk\+Graph} has been distributed. \doxylink{requirements_The}{The} local index will be a value between 0 and \doxylink{classvtk_graph_a1acbb7b69387ec2a08956d1d9d11c679}{Get\+Number\+Of\+Vertices()}, for vertices, or \doxylink{classvtk_graph_ac3534f310838e2303919825f0ec436ff}{Get\+Number\+Of\+Edges()}, for edges, and can be used to access the local parts of distributed data arrays. When given a vtk\+Id\+Type identifying a vertex, one can determine the owner of the vertex with \doxylink{classvtk_distributed_graph_helper_a2390d21b6b5794e2d3515d211d2e19fe}{vtk\+Distributed\+Graph\+Helper::\+\+Get\+Vertex\+Owner()} and the local index with \doxylink{classvtk_distributed_graph_helper_abe8de15d0f2f5ed9cacbd43026ae83da}{vtk\+Distributed\+Graph\+Helper::\+\+Get\+Vertex\+Index()}. With edges, the appropriate methods are \doxylink{classvtk_distributed_graph_helper_a059bdfb8e851f886ac9834bd5e0d61ba}{vtk\+Distributed\+Graph\+Helper::\+\+Get\+Edge\+Owner()} and \doxylink{classvtk_distributed_graph_helper_a4a321aa8e443c7e08c6bc8d5c6df1c18}{vtk\+Distributed\+Graph\+Helper::\+\+Get\+Edge\+Index()}, respectively. To construct a vtk\+Id\+Type representing either a vertex or edge given only its owner and local index, use \doxylink{classvtk_distributed_graph_helper_a1aa236e2ac760b9e2d72157889609e38}{vtk\+Distributed\+Graph\+Helper::\+\+Make\+Distributed\+Id()}.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Distributed graphs:\+}
\doxylink{requirements_The}{The} edges in a distributed graph are always stored on the processors that own the vertices named by the edge. For example, given a directed edge (u, v), the edge will be stored in the out-\/edges list for vertex u on the processor that owns u, and in the in-\/edges list for vertex v on the processor that owns v. This "{}row-\/wise"{} decomposition of the graph means that, for any vertex that is local to a processor, that processor can look at all of the incoming and outgoing edges of the graph. Processors cannot, however, access the incoming or outgoing edge lists of vertex owned by other processors. Vertices owned by other processors will not be encountered when traversing the vertex list via \doxylink{classvtk_graph_aeeed05aabf5e82e2fb934756482d9cf2}{Get\+Vertices()}, but may be encountered by traversing the in-\/ and out-\/edge lists of local vertices or the edge list.
\end{DoxyParagraph}
\begin{DoxyParagraph}{Distributed graphs:\+}
Distributed graphs can have pedigree IDs for the vertices in the same way that non-\/distributed graphs can. In this case, the distribution of the vertices in the graph is based on pedigree ID. For example, a vertex with the pedigree ID "{}\+Here"{} might land on processor 0 while a vertex pedigree ID "{}\+There"{} would end up on processor 3. By default, the pedigree IDs themselves are hashed to give a random (and, hopefully, even) distribution of the vertices. However, one can provide a different vertex distribution function by calling \doxylink{classvtk_distributed_graph_helper_a65c2ce8d5da5908b514dd564f120445a}{vtk\+Distributed\+Graph\+Helper::\+\+Set\+Vertex\+Pedigree\+Id\+Distribution}. Once a distributed graph has pedigree IDs, the no-\/argument Add\+Vertex() method can no longer be used. Additionally, once a vertex has a pedigree ID, that pedigree ID should not be changed unless the user can guarantee that the vertex distribution will still map that vertex to the same processor where it already resides.
