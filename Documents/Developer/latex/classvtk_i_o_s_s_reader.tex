\doxysubsection{Detailed Description}
Reader for IOSS (Sierra IO System). 

\doxylink{classvtk_i_o_s_s_reader}{vtk\+IOSSReader} is reader that uses the IOSS (Sierra IO System) library to read files. Currently, this reader support Exodus and CGNS file formats. IOSS imposes certain restrictions on these file formats and hence it may not be possible to open every Exodus or CGNS file using this reader. This is true especially for CGNS, more so than Exodus. In that case {\ttfamily \doxylink{classvtk_c_g_n_s_reader}{vtk\+CGNSReader}} may be more appropriate.\hypertarget{classvtk_i_o_s_s_reader_SpecifyingFiles}{}\doxysubsection{\texorpdfstring{Specifying Files}{Specifying Files}}\label{classvtk_i_o_s_s_reader_SpecifyingFiles}
One can select a single file to read using {\ttfamily \doxylink{classvtk_i_o_s_s_reader_a7e0ab0000098fef2428c2186ea20ee4a}{vtk\+IOSSReader::\+\+Set\+File\+Name}}. With IOSS, however, it is not uncommon to have a collection of files named using standard patterns (described in Section \doxysectlink{classvtk_i_o_s_s_reader_IossNamingConventions}{IOSS Naming Conventions}{1}). To support this use-\/case, the reader automatically scans for additionally files internally. To disable this behaviour, call {\ttfamily vtk\+IOSSReader::\+\+Scan\+For\+Related\+Files\+Off}.

Alternatively, the list of files to be read can be explicitly specified using {\ttfamily \doxylink{classvtk_i_o_s_s_reader_a15d8aad385fd45299367e4c64905e5e0}{vtk\+IOSSReader::\+\+Add\+File\+Name}}. Then too, if {\ttfamily Scan\+For\+Related\+Files} is {\ttfamily true}, the reader will search for related files for each of the files specified.

Additionally, {\ttfamily File\+Range} and {\ttfamily File\+Stride} may be used to limit to reading a subset of files.\hypertarget{classvtk_i_o_s_s_reader_SelectingBlocksSets}{}\doxysubsection{\texorpdfstring{Selecting blocks and sets to read}{Selecting blocks and sets to read}}\label{classvtk_i_o_s_s_reader_SelectingBlocksSets}
An IOSS file comprises of blocks and sets of various types. These are described by the enum {\ttfamily vtk\+IOSSReader::\+\+Entity\+Type}.

{\ttfamily vtk\+IOSSReader::\+\+Get\+Entity\+Selection} returns a {\ttfamily \doxylink{classvtk_data_array_selection}{vtk\+Data\+Array\+Selection}} instance for each of the entity types. This {\ttfamily \doxylink{classvtk_data_array_selection}{vtk\+Data\+Array\+Selection}} can be used to query the names for available blocks or sets and also select which ones to read.

Typical usage is as follows:\+


\begin{DoxyCode}{0}

\end{DoxyCode}


By default, all blocks are enabled, while all sets are disabled.

In additional to selecting blocks and sets by name, if the file defines assemblies that organize these blocks and sets, then one can use selector expressions to enable blocks/\+sets as defined in the assemblies.

A block (or set) is treated as enabled if it is either explicitly enabled using the block selection or implicitly enabled due to a selector specified on over the assemblies.

Typical usage to select blocks by assembly alone is as follows:\+


\begin{DoxyCode}{0}

\end{DoxyCode}
\hypertarget{classvtk_i_o_s_s_reader_SelectingArrays}{}\doxysubsection{\texorpdfstring{Selecting arrays to read}{Selecting arrays to read}}\label{classvtk_i_o_s_s_reader_SelectingArrays}
Similar to the block and set selection, arrays (or fields as IOSS refers to them) to read from each of the blocks or sets can be specified using the {\ttfamily \doxylink{classvtk_data_array_selection}{vtk\+Data\+Array\+Selection}} instance returned using {\ttfamily vtk\+IOSSReader::\+\+Get\+Field\+Selection} (or one of its convenience variants).

By default all arrays are enabled.\hypertarget{classvtk_i_o_s_s_reader_IossNamingConventions}{}\doxysubsection{\texorpdfstring{IOSS Naming Conventions}{IOSS Naming Conventions}}\label{classvtk_i_o_s_s_reader_IossNamingConventions}
An IOSS complete dataset is referred to as a database. There can be multiple multiple timesteps in a single database. A single database may split among multiple files. When a database is split among multiple files, this is strictly spatial partitioning with each file storing part of the data for a specific partition. In this case, the files are named with suffix {\ttfamily .\{NP\}.\{RANK\}} where {\ttfamily \{NP\}} is the total number of partitions and {\ttfamily \{RANK\}} is the partition number. For example, if database named {\ttfamily can.\+e} is split among four files representing 4 partitions, it will be named as follows:\+

\begin{DoxyVerb}*  can.e.4.0
*  can.e.4.1
*  can.e.4.2
*  can.e.4.3
* \end{DoxyVerb}


In this example, the database name is {\ttfamily can.\+e} while the {\ttfamily .4.\+[0-\/4]\+} suffix provides the partition information.

Note, the database need not be split into multiple files. Thus, a writer may generate a single {\ttfamily can.\+e} file that has all the timesteps and partitions and still provide all information available when the database is split among multiple files.

Multiple databases (with each stored in a single file or spatially split among files) can form a temporal sequence. This done by using another file naming convention. If the database name is followed by {\ttfamily -\/s.\{RS\}}, where {\ttfamily \{RS\}} is some number sequence), then the databases are treated as a temporal sequence with {\ttfamily \{RS\}} (called restart numbers) representing the temporal sequence order.

\doxylink{requirements_The}{The} follow represents a temporal sequence:\+

\begin{DoxyVerb}*  mysimoutput.e-s.000
*  mysimoutput.e-s.001
*  mysimoutput.e-s.002
* \end{DoxyVerb}


You can use any number of digits for the restart number, but by convention the number used should be the same for all files. Also by convention, you can leave off the {\ttfamily -\/s.\{RS\}} suffix for the first file. \doxylink{requirements_The}{The} following sequence is internally the same as that above:\+

\begin{DoxyVerb}*  mysimoutput.e-s
*  mysimoutput.e-s.001
*  mysimoutput.e-s.002
* \end{DoxyVerb}


When a database in the temporal sequence is spatially split in multiple files, the corresponding filename is suffixed by the partition information. For example:\+

\begin{DoxyVerb}*  mysimoutput.e-s.2.0
*  mysimoutput.e-s.2.1
*  mysimoutput.e-s.001.2.0
*  mysimoutput.e-s.001.2.1
*  mysimoutput.e-s.002.2.0
*  mysimoutput.e-s.002.2.1
* \end{DoxyVerb}


In this case, the filenames take the form {\ttfamily \{DBNAME\}-\/s.\{RS\}.\{NP\}.\{RANK\}}, where {\ttfamily \{DBNAME\}} is the database name, {\ttfamily \{RS\}} is the restart number, {\ttfamily \{NP\}} is the number of spatial partitions and {\ttfamily \{RANK\}} is the spatial partition number.\hypertarget{classvtk_i_o_s_s_reader_References}{}\doxysubsection{\texorpdfstring{References}{References}}\label{classvtk_i_o_s_s_reader_References}

This provides a mechanism to limit to reading to certain files in a spatially partitioned file-\/series. To just specific subset of files, one can always simply specify those files using {\ttfamily \doxylink{classvtk_i_o_s_s_reader_a15d8aad385fd45299367e4c64905e5e0}{Add\+File\+Name}} and then set {\ttfamily Scan\+For\+Related\+Files} to false. Another way is to let the reader scan for all related files and then use {\ttfamily File\+Range} and {\ttfamily File\+Stride} to limit which files are read.

If the range is invalid, i.\+e. {\ttfamily File\+Range\+[0]\+ \texorpdfstring{$>$}{>}= File\+Range\+[1]\+}, it\textquotesingle{}s assumed that no file-\/range overrides have been specified and both File\+Range and File\+Stride will be ignored. When valid, only the chosen subset of files will be processed.
